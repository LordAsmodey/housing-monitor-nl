# Implement Feature

Применяй только по явному вызову пользователя; сообщи о включении режима.
Команда без описания использует однозначную задачу из текущего диалога; если
цель не определена, уточни её. Не запускай pipeline по размеру задачи или
просто слову «реализуй». Обычные задачи остаются в обычном режиме.

## Контракт оркестратора

Основной агент читает `.codex/agents/orchestrator.toml` и принимает эту роль.
Не создавай отдельного координатора ради формальности. Не пиши/исправляй
код, тесты, документацию, конфиги, миграции, прототипы или план реализации.
Любую содержательную правку поручай соответствующему агенту, даже после review.
Чтение/diff, координация, проверка результатов и Git/PR в рамках задачи разрешены.

Перед стартом прочитай корневой `AGENTS.md`, `.codex/agent-context.md`,
`docs/subagents.md` (запуск/реестр) и [execution.md](references/execution.md).
Для failure/retry/test phase — [verification.md](references/verification.md).
Профильные Notion/код читай адресно, не повторяй неизменившиеся чтения.

## Последовательность

1. Установи scope/требования, текущую integration base и prerequisites. Для v2
   base/ref и target PR — `codex/platform-v2`, отдельный task checkout.
2. Architect по необходимости: новый flow/API/module, изменение границ, данных,
   безопасности или миграции. Он создаёт архитектуру; Orchestrator не подменяет его.
3. Planner обязательно: tasks, scopes, acceptance criteria, dependencies/phases.
   Проверь валидность; исправление плана верни Planner.
4. Для каждой задачи Worker → соответствующий независимый Reviewer.
   Независимые parallel groups запускай в пределах слотов и без общих ресурсов.
5. Test phase: frontend-tester → backend-tester → e2e-tester. Вызови каждую роль;
   нет относящегося scope — она возвращает обоснованный SKIPPED, не исчезает
   из процесса. Обязательный непроверенный критерий означает BLOCKED.
6. Docs phase: docs-writer с итогом задач, evidence и optional ADR.
7. Проверь итоговый diff/критерии, сведи тесты и ограничения, подготовь PR если
   поручено. Не объявляй весь feature готовым при frozen/blocked prerequisites.

Review/test/design допускают один начальный запуск и максимум **три цикла
исправления и повторной проверки**. Точные счётчики — verification.md.
Не обходи лимит новым task ID/агентом и не продолжай зависимые задачи после
неудачи prerequisite. Сбой среды не маскируй как дефект продукта или PASSED.

Если готов прототип, передай его путь Planner и frontend-worker. Design pipeline
сам по себе не запускается: для него есть отдельный `design-feature`.
Если custom role не распознана, используй общий субагент с явной загрузкой
TOML роли. Если делегирование недоступно вообще — сообщи BLOCKED, не реализуй сам.
