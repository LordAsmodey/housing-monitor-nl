# Админка v1

Согласованные требования и прогресс: [Notion](https://app.notion.com/p/3fad10c6e6ab810f8b6ac405dee44aeb).

Отдельное React-приложение находится в `admin/`, API — в `src/admin/`.
В production приложение NestJS отдаёт собранную статику по `/admin/` и API по `/api/admin/`.
Отдельный сервис для UI не нужен. Раздельные frontend/backend остаются в одном репозитории.

## Запуск

```sh
npm ci
npm ci --prefix admin
npm run db:generate
npm run db:deploy
npm run build:all
node --env-file=.env dist/main.js
```

В `.env` задайте `ADMIN_LOGIN` и `ADMIN_PASSWORD`. Начальные учётные данные по указанию
владельца записаны только в локальный игнорируемый `.env`; в git они не входят.
На другом компьютере или хостинге переменные нужно настроить отдельно. Без обеих
переменных вход выключен. Пароль не передаётся в Vite и не попадает в bundle.

Для разработки запустите backend и `npm run admin:dev` в отдельных терминалах.
Vite проксирует API к localhost:3000. Страница — `http://localhost:5173/admin/`.
При NODE_ENV=production cookie требует HTTPS; локально используйте development.

## Поведение

- Редактируются месячная аренда, радиус там, где его поддерживает поиск, и минимальная
  площадь. Для Woldring ограничение бюджета необязательно. Groningen и фиксированные
  условия сегодняшних публикаций Funda / заселения Huurwoningen остаются прежними.
  Сумма аренды — объявленная цена; servicekosten не прибавляются автоматически.
- Включение/отключение хранится отдельно от здоровья источника. Отключение прекращает
  будущие проверки; уже выполняющаяся проверка завершается с прежними настройками.
  Оно не отменяет уже созданные уведомления outbox. Настройки подключения и серверные
  env-флаги по-прежнему обязательны.
- Все фильтры валидируются на сервере. Цена и радиус Funda/Huurwoningen/Vesteda
  передаются в запрос к сайту. Бюджет Woldring/Gruno и минимальная площадь применяются
  к уведомлениям на сервере. Неподходящие прочитанные объявления тоже сохраняются
  для дедупликации. Неизвестная площадь не проходит заданный минимум.
- Каждое изменение создаёт новую revision и запись истории. Если версия формы устарела,
  API возвращает 409. Кнопка отмены загружает последние полученные настройки; после
  конфликта сначала обновите данные кнопкой «Обновить».
- При смене фильтров или повторном включении первый **полный успешный** сбор новой
  версии молча фиксирует текущую выдачу. Следующие сборы уведомляют о новых подходящих
  объявлениях; прежние ID и baseline сохраняются. Возврат доступности уже известных
  объектов сохраняет существующие правила дедупликации.
- Это консервативная граница «только будущие»: объявления, появившиеся между сохранением
  фильтров и первым успешным сбором, также входят в тихую выдачу. Сайты не гарантируют
  точный publishedAt, поэтому обещать границу до секунды сохранения нельзя.
- Начатая проверка хранит snapshot и revision. Завершение старой проверки не помечает
  более новую версию применённой. Ошибка/неполная выдача не применяет настройки,
  не меняет baseline/lastSuccessAt и не превращается в успешный ноль.
- UI обновляет мониторинг раз в 15 секунд, сохраняя несохранённые изменения формы.
  Показывает последние 10 проверок, последние 30 изменений и числа записей outbox
  по статусам. Найдено — число валидно прочитанных объявлений до серверных фильтров.

## Архитектура

`scripts/search-settings.cjs` — реестр; отдельные модули источников находятся в
`scripts/search-modules/`: поля, значения по умолчанию,
диапазоны, query/server, проверка и построение запросов. Интерфейс строит формы из
описания API. Адаптеры сохраняют URL allowlists и проверку полноты выдачи.

`SearchConfiguration` отделён от адаптера и SiteProfile; пока одна настройка на источник
для владельца `admin`. `SearchChange` хранит историю, `MonitoringRun` — снимок.
Распределённый PostgreSQL lease и блокировка строки источника сериализуют claim и
сохранение настроек, сетевой сбор идёт вне транзакций. Физический сбор пока выполняется
для одной настройки. Будущие пользователи потребуют отдельных subscriptions/search IDs,
разрешений, привязки Telegram и объединения одинаковых сборов; эти механизмы ещё не
реализованы. Не следует просто выдавать другим людям доступ к этой админке.

Авторизация использует случайные серверные сессии на 8 часов, хеш токена в PostgreSQL,
HttpOnly/SameSite cookie, CSRF token для изменений и ограничение попыток входа в процессе.
Ограничение входа пока локально одному процессу; перед масштабированием login на несколько
реплик потребуется общий rate limiter. Сессия переживает перезапуск приложения.

## Проверка и выпуск

```sh
node test/admin-settings.test.mjs
npm run typecheck
npm test
npm run admin:build
npm run build
npm run db:validate
# Только disposable PostgreSQL, без загрузки production .env:
DATABASE_URL=postgresql://housing:test@localhost:55432/housing npm run test:integration
```

Интеграционные файлы выполняются последовательно, поскольку используют общую тестовую БД.
Проверяются тихая выдача после изменения, будущие уведомления, pause, конфликт версий,
старый snapshot, ошибка сбора, HTTP вход, CSRF и logout.

Сначала применить миграцию и обновить browser workers, затем приложение. Browser protocol
передаёт настройки и проверяет fingerprint в ответе; старый worker приводит к
`BROWSER_SETTINGS_UNSUPPORTED`, а не к тихому использованию неправильных фильтров.
Перед выпуском нужны read-only live smoke изменённых запросов и проверка UI в браузере.
Откат приложения: вернуть прежний образ; добавочные таблицы можно оставить. Старый код
не учитывает pause/фильтры из админки — при откате восстанавливаются фиксированные поиски.

Ветка обновлена до актуального main `a8494ae`, включая Gruno. Его модуль учитывает
настраиваемый максимальный бюджет уже при выборе карточек для подробного чтения;
минимальная цена и площадь применяются к уведомлениям. Правила подтверждённой
доступности и состава цены сохранены.

## Результаты проверки в этой среде

- Frontend зависимости установлены, добавлен `admin/package-lock.json`; Docker/CI
  используют `npm ci`. React/TypeScript/Vite production build прошёл.
- Схема Prisma проверена официальным WASM-парсером. Backend прошёл strict typecheck
  и компиляцию с типами временного клиента, сгенерированного из той же схемы.
- Unit-тесты проходят (итоговое число указано в Notion).
- SQL всех четырёх миграций выполнен на отдельном PostgreSQL 17 в Docker.
- 21 интеграционный тест прошёл с реальной PostgreSQL через официальный JS-адаптер
  Prisma 6.19.3. Временный клиент/адаптер и тестовая подмена модуля находятся вне
  репозитория; schema.prisma, PrismaService и production-зависимости на этот режим
  не переводились. Это дополнительная проверка логики, а не подтверждение работы
  штатного нативного движка.
- Собранный React + весь NestJS AppModule + тестовая PostgreSQL проверены в Chromium:
  неверный/верный вход, пять источников, сохранение фильтров в БД, включение/выключение,
  история/версии, сохранение черновика при обновлении, выход, CSP, мобильная ширина,
  отсутствие JS-ошибок. Внешние источники и Telegram в этом тесте не вызывались.

Прокси среды всё ещё отклоняет `binaries.prisma.sh` с HTTP 403. До выпуска нужно
разрешить этот домен и выполнить штатные `db:generate`, `db:deploy`, `typecheck`,
`build`, `test:integration` и Docker build с нативным клиентом. Также остаются read-only
live smoke изменённых query-параметров сайтов и проверка протокола с обновлёнными
настоящими workers. Production-развёртывание не выполнялось.
