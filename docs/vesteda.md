# Vesteda

[Согласованные требования в Notion](https://app.notion.com/p/402d10c6e6ab81769d81ce16ba836c73?pvs=204). Runbook описывает реализацию;
датированные результаты ниже относятся к конкретным проверкам, а не live-статусу production.

Источник `vesteda:groningen-20km-500-1500` подготовлен для scheduler приложения:
проверка каждые `MONITOR_INTERVAL_SECONDS` (900 секунд по умолчанию), собственные baseline
и PostgreSQL lease, существующий Telegram outbox. Новый browser service и аккаунт не нужны.

## Статус включения

Пользователь 12.10.2026 подтвердил наличие письменного разрешения и явно попросил включить мониторинг.
Источник **включён по умолчанию** после развёртывания; `VESTEDA_MONITORING_ENABLED=false`
приостанавливает его без сброса baseline.
[Disclaimer Vesteda](https://www.vesteda.com/nl/disclaimer), проверенный 12.10.2026,
прямо требует предварительного письменного разрешения на scraping, распространение
и deep links; отдельно допускается скачивание для личного использования.
`robots.txt` не содержит Disallow, но это не отменяет условия сайта.
Разрешение подтверждено пользователем в чате; сам документ разрешения в репозитории не хранится.
Приложение с выключенным флагом не создаёт источник и не читает API.
Официальная альтернатива на странице поиска — email alerts через аккаунт
https://hurenbij.vesteda.com/inschrijven/ . Email-интеграция в этот адаптер не входит.

[Пользовательский поиск](https://www.vesteda.com/nl/woning-zoeken?placeType=1&sortType=0&radius=20&s=Groningen,+Nederland&sc=woning&latitude=53.219383&longitude=6.5665016&filters=&priceFrom=500&priceTo=1500):
Groningen, радиус 20 км, аренда €500–1500. Параметры передаются публичному
`POST https://www.vesteda.com/api/units/search/facet` так же, как в клиенте сайта.
Пустой `filters=` преобразуется клиентом в `[0]`; `sortType` передаётся как `sorting`.
Цена и география фильтруются сайтом; дополнительные ограничения свежести и заселения не добавляются.

Проверяются `count`, `objectsCount`, `complexesCount`, `newComplexesCount` и длины всех массивов.
Выдача relevance (`sortType=0`) приходит целиком одним запросом без пагинации.
Жилые комплексы не являются конкретными доступными квартирами и не сохраняются как объявления.
Сохраняются все квартиры из `objects`: `status=1/5` доступны, `2/3/4` сданы или зарезервированы.
Неизвестный статус, повреждённая карточка, дубль или неполная выдача означают сбой проверки.
Первый успешный запуск заполняет baseline без рассылки; далее уведомляются новые доступные
квартиры и переходы `unavailable → available`. На объект и Telegram-канал — одно уведомление.

Цена читается из точного `priceUnformatted`, а не округлённого текста `price`.
Уведомление содержит адрес, город, аренду, площадь и ссылку.
Сервисные расходы и дата публикации отсутствуют в ответе и не выдумываются.
`numberOfBedRooms` не выдаётся за общее число комнат.

Адаптер написан на TypeScript; внешние данные проверяются Zod. Общий существующий runner CJS
сохраняет транзакции, lease, baseline, retries/cooldown и статусы источника.
Обновления аренды, площади и доступности записываются также для источников без `housingDetails`.
Сетевая ошибка и 502/503/504 получают не более трёх попыток; лимиты — 120 секунд и 8 МБ.
Redirect не выполняется. 401/403 переводят источник в BLOCKED с повтором через 6 часов,
429 включает cooldown. Ошибка не меняет последний успех или baseline.

Read-only live smoke: `npm run build && node scripts/vesteda-check.cjs`.
Команда не обращается к БД и не отправляет Telegram/Sentry.
Fixtures получены из публичного API 12.10.2026: 15 квартир, 2 доступны, 2 комплекса.
Unit: `node --import tsx --test test/vesteda.test.ts`; интеграционные проверки входят в
`npm run test:integration`. GitHub live workflow проверяет API перед merge; доступен ручной запуск.
