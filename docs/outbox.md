# PostgreSQL и Telegram outbox

## Запуск

Применить `npm run db:deploy`, затем запустить приложение. Prisma Client генерируется
до компиляции (`npm run db:generate`). Docker-образ содержит Prisma CLI и миграции;
Railway выполняет db:deploy как pre-deploy command, Compose — перед стартом приложения.
`/health/ready` отвечает 503, если БД недоступна или таблица outbox отсутствует.
Redis пока не используется: worker читает очередь напрямую из PostgreSQL.

Для доставки в одной группе установить в секретах приложения:

```dotenv
TELEGRAM_DELIVERY_ENABLED=true
TELEGRAM_BOT_TOKEN=<токен>
TELEGRAM_CHAT_ID=<отрицательный ID группы>
TELEGRAM_MAX_ATTEMPTS=5
```

По умолчанию доставка выключена. Изменение назначения не перенаправляет старые задания:
worker выбирает только задания для текущего TELEGRAM_CHAT_ID. Запуск приложения
не создаёт тестовых объявлений и не отправляет тестовое сообщение.

## Запись объявлений

Будущий executor вызывает `ListingsService.recordValidatedRun` только после проверки
результата источника. Все объявления, baseline и outbox записываются одной транзакцией.
Блокировка Source предотвращает гонку параллельных первых запусков. Первый валидный
проход, включая пустую выдачу, создаёт baseline без уведомлений. Повторный externalId
или URL fingerprint обновляет lastSeenAt без нового задания. Изменение цены/доступности
и межсайтовое сопоставление остаются отдельными следующими задачами.
Этот внутренний метод не открывает публичный HTTP endpoint для записи.

## Доставка и ограничения

Глобальная блокировка PostgreSQL и DeliveryGate сериализуют отправку для одного бота
между экземплярами приложения. После попытки сохраняется пауза не меньше 3,1 секунды;
429 увеличивает паузу согласно retry_after, backoff и jitter. Одна попытка HTTP имеет
тайм-аут 15 секунд, резервирование задания — 60 секунд. Ошибки 400/401/403 идут в
DEAD_LETTER; подтверждённый 429 повторяется до TELEGRAM_MAX_ATTEMPTS. Сетевые ошибки,
5xx, некорректный ответ или прерванная отправка идут в UNCERTAIN без автоматического
повтора. Уникальный idempotencyKey исключает повторную постановку внутри приложения.

Telegram не предоставляет клиентский ключ идемпотентности. После доставки и сбоя
до сохранения message ID невозможно автоматически установить результат; поэтому
exactly-once не гарантируется. Администратор проверяет группу перед решением.

## Диагностика

`npm run outbox:admin -- list` показывает до 100 UNCERTAIN/DEAD_LETTER заданий,
только ID, статусы, число попыток, категорию ошибки и время; без содержимого и секретов.

Если сообщение найдено в группе:

```sh
npm run outbox:admin -- sent <outboxId> <telegramMessageId>
```

После проверки группы и устранения причины можно явно повторить:

```sh
npm run outbox:admin -- retry <outboxId> --accept-duplicate-risk
```

Повтор UNCERTAIN может создать дубль. Для DEAD_LETTER сначала исправьте токен,
права бота или назначение; смена ID группы требует отдельного исправления задания.
Команды администратора не публикуются как HTTP API. Логи содержат только безопасные
категории ошибок. Фото, Telegram-команды и admin alerts пока не реализованы.

## Интеграционные проверки

`npm run test:integration` требует явного DATABASE_URL отдельной одноразовой БД,
с применёнными миграциями. Не используйте production: тесты создают временный trigger
и очищают DeliveryGate. CI поднимает отдельный PostgreSQL 17 и выполняет эти тесты.
Проверяются baseline, дедупликация, rollback транзакции, параллельные worker,
сохранение ограничения частоты, 429, лимит попыток и неоднозначная доставка.
