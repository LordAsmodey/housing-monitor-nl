# Rentola — Groningen

[Согласованные требования в Notion](https://app.notion.com/p/402d10c6e6ab81e9adaaeb9b92e2baed?pvs=204). Runbook описывает реализацию;
датированные результаты ниже относятся к конкретным проверкам, а не live-статусу production.

Поиск: https://rentola.nl/en/rent?location=240117&order=desc

Критерии: Groningen, объявленная месячная аренда до €1500 включительно, самостоятельное жильё без комнат. Дата публикации не ограничена, дополнительные расходы из описаний к цене не прибавляются. Source ID: `rentola:groningen-homes`. HTTP GET без аккаунта, browser worker и LLM; цена и площадь фильтруются локально, исходная ссылка сохраняется.

## Режим сбора, согласованный 19 октября 2026

Каждые 900 секунд адаптер читает максимум первые две страницы поиска в исходной сортировке `order=desc` (до 42 карточек). При короткой странице останавливается раньше. Это выбранное окно обнаружения; увеличение окна при большом количестве новых объявлений не предусмотрено. Точное поле времени, определяющее порядок Rentola, публичным контрактом не подтверждено.

Первый запуск нового состояния, первичный baseline, смена фильтров/revision и ежедневная сверка обходят всю фактически доступную выдачу. Полная сверка назначается через 24 часа после начала предыдущей успешной полной сверки. Время хранится в PostgreSQL, перезапуск приложения не сбрасывает расписание. Изменение фильтров заново проверяет описания и сохраняет тихий baseline. Наличие прежних HousingListing сохраняет дедупликацию при первом заполнении нового кэша после обновления.

**`totalCount` и `totalPages` вообще не участвуют в принятии решений**, включая валидацию и выбор последней страницы. Нет сравнения общего количества, проверки размера последней страницы по счётчику и повторного обхода с `rent_asc`. Конец определяется фактической короткой страницей (меньше 21 карточки); при точном кратном 21 требуется согласованный пустой ответ следующей страницы. Для пустой страницы проверяются эхо запроса и пустой JSON-LD; её номер в метаданных может быть уменьшен сервером. Пустая первая страница по-прежнему даёт `EMPTY_SEARCH_UNCONFIRMED`, а не успешный ноль.

Совпадение ID на границе страниц дедуплицируется; более позднее наблюдение определяет поля и доступность. Противоречие идентичности URL/ID, повтор целой полной страницы, превышение 100 страниц, HTTP-сбой, блокировка или нарушение структуры завершают запуск ошибкой. Отдельные страницы не являются снимком на единый момент: повторные обходы снижают риск пропусков при перестановках, но не дают гарантии полного snapshot.

## Описания и сохранение результатов проверок

Новые или изменившиеся подходящие по карточке кандидаты проходят свежую проверку описания. Решения по уже проверенным кандидатам хранятся в `SourceCollectionState`, включая отклонённые комнаты. При совпадении данных карточки и фильтров решение используется повторно до 24 часов. Полная ежедневная сверка повторно проверяет все текущие подходящие по карточкам кандидаты; описания могут измениться без изменения карточки. Это осознанная задержка обнаружения таких изменений до следующей сверки.

Изменения цены, площади, названия, адреса, URL или доступности требуют новой проверки. Если карточка становится недоступной, неизвестной или перестаёт соответствовать условиям, прежнее решение исключается из кэша. Полная сверка удаляет кэш отсутствующих кандидатов. Отсутствие объявления в просмотренных страницах не помечает HousingListing как снятое.

Новое уведомление формируется только для проверенного кандидата. Повторное использование положительного решения относится к объектам, уже записанным вместе с этим решением в предыдущей транзакции. Кэш, HousingListing, baseline/revision, статус запуска и transactional outbox записываются атомарно после проверки владения lease. При сбое или потере lease кэш и время полной сверки не продвигаются. Ошибка не превращается в успешный пустой результат.

## Проверка объявлений

Next.js `self.__next_f.push` декодируется как JSON без исполнения JavaScript. Проверяются эхо location/order/page и отсутствие неожиданных фильтров, город карточек и included, размер страницы не больше 21, уникальность ID/URL внутри страницы. JSON-LD сверяется с данными карточек: URL, название, цена, валюта, адрес и количество элементов. Межстраничные повторы допускаются, конфликты идентичности — нет.

Категории Rentola ненадёжны: реальное объявление Jennerstraat 12 имеет категорию apartment, но описание предлагает комнаты. Поэтому проверяются тип, название и описание. Комнаты, совместные кухня/санузел, неизвестные категории, неоднозначные house и пустые описания исключаются. Правила консервативны и могут исключить полноценное жильё при неоднозначном тексте. Только InStock одновременно в карточке и проверенном описании допускает объект; unknown не уведомляется. Это утверждение агрегатора, а не подтверждение арендодателя.

Оценочная площадь не считается известной. При заданном минимуме площади объект без достоверного значения исключается. URL деталей: только HTTPS rentola.nl, без credentials, query и hash, с проверенным шаблоном slug. Ссылка ведёт на Rentola; платный контакт с арендодателем не используется.

## Расписание, границы и наблюдаемость

Интервал — 900 секунд. Общий бюджет — 240 секунд, lease — 300 секунд (сбор + commit + запас). Страницы идут последовательно с паузой 300 мс; детали — максимум два одновременно со сдвигом старта и паузами 300 мс. Тело ограничено 8 MiB. Транспортные ошибки и HTTP 502/503/504 повторяются до трёх попыток; 429 даёт cooldown, 401/403 — BLOCKED. Заголовок `Accept-Language: en` соответствует URL; неожиданные редиректы запрещены.

В `MonitoringRun.collectionScope` записывается `head` или `catalog`. Админка показывает «Первые 2 страницы» или «Вся выдача»; catalog означает достигнутый конец обхода, а не snapshot. Логи успешного запуска содержат режим, число уникальных ID, страниц, новых detail-проверок, использованных решений и время. Счётчик сайта в них не нужен. Старые записи истории имеют пустой scope.

Админка позволяет менять цену/площадь и приостанавливать источник. `RENTOLA_MONITORING_ENABLED=false` отключает источник без удаления истории. Приложение применяет миграцию `20261019120000_collection_state`: новая таблица состояния и nullable поле охвата истории, без изменения существующих объявлений и уведомлений.

## Проверки

```sh
node --import tsx --test test/rentola.test.ts
npm run test:integration
node --import tsx scripts/rentola-check.cjs
```

Unit-сценарии: независимость от счётчиков, две полные страницы без третьей, межстраничные повторы, ежедневный обход, повторное использование принятых и отклонённых решений после восстановления состояния, изменение карточки/фильтров/доступности, пустой конец, цикл пагинации, лимит страниц, отмена и отказные HTTP-сценарии. Реальные fixtures первой/последней страниц и ошибочно классифицированной комнаты сохранены.

PostgreSQL integration проверяет тихий baseline, сохранение кэша, новые уведомления без дублей, ежедневную перепроверку, атомарный rollback состояния вместе с объявлениями/outbox, потерю lease, тихую смену фильтров и pause. Live smoke без БД и Telegram выполняет полный обход и следующий head-проход с полученным состоянием; печатает оба результата.

Исследование причин и альтернатив: [rentola-pagination-2026-10-19.md](research/rentola-pagination-2026-10-19.md). Предыдущие изменения сортировки/таймаута давали отдельные успешные проходы, но не устранили `SEARCH_CHANGED_DURING_RUN`; текущая реализация меняет сам контракт обхода.
