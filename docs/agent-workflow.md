# Работа с контекстом и диагностикой

Эти правила применяются по теме задачи. Они не заменяют требования Notion и разрешения пользователя; отдельного учёта токенов или установки инструментов не требуют.

## Чтение

- Используйте [индекс](index.md), прямую профильную страницу и относящийся к задаче runbook.
- Для поиска кода сначала пути (`rg --files`), затем совпадения (`rg -n`) и нужный диапазон строк. Исключайте generated/build/vendor, если они не являются предметом расследования.
- Архивы и исследования открывайте для конкретного исторического вопроса. Перевод всего проекта и дублирование требований не нужны.
- Уже полученный документ используйте повторно из контекста задачи. Обновляйте его, если есть причина ожидать изменения.

## Ответы инструментов

- Прежде чем вернуть большой JSON или результат MCP модели, выберите нужные поля/разделы кодом. Не выводите одновременно одинаковые данные из text и structuredContent.
- Для статуса источников обычно достаточно имени, enabled/status, последней попытки/успеха, следующей проверки, категории ошибки и сводки outbox. Данные объявлений и полная история нужны для адресного расследования.
- Ограничивайте логи сервисом, временем и run ID. При большом объёме сохраняйте оригинал во временный файл, затем выводите относящиеся к гипотезе строки, контекст ошибки и итог.
- Успешные тесты возвращайте сводкой. При ошибке сохраняйте exit code, название теста, assertion, причину и нужный stack trace. Сокращение вывода не должно скрывать сбой.
- Скриншоты передавайте как изображения; не печатайте base64. Используйте браузер для UI/визуальных вопросов; состояние, доступное через достаточный API/CLI, получайте напрямую.
- Независимые чтения объединяйте в один вызов. Учитывайте общий объём результата; не объединяйте десятки полных документов в один вывод.
- При ожидании долгой операции используйте её session/job ID и разумный интервал. Не запускайте повторно сбор, деплой или полный аудит только ради обновления статуса.

## Проверки и границы задачи

Выбирайте проверки по затронутому поведению и обязательным требованиям CI. После успешного набора расширяйте или повторяйте его при новых изменениях, сбое или конкретном риске. Не меняйте обработку ошибок, baseline, доступность или фильтры под видом сокращения контекста.

Production-диагностика нужна для задачи эксплуатации, выпуска или подтверждения специфичного production-сбоя. Локальное исправление документации не требует обращения к Railway/БД/Sentry или live-сайтам. Live smoke, тестовая БД, CI и штатный production run — разные виды подтверждения.

## Передача контекста

Независимую большую задачу удобно начинать в отдельной сессии. Продолжайте связанные исправления в текущей; не дробите каждый шаг на новый чат.

При переносе оставляйте короткую записку:
- цель и принятые решения;
- профильная страница требований и нужные пути;
- изменённые файлы и результаты проверок;
- оставшиеся действия и конкретные ограничения.

Не копируйте полную историю инструментов, логи и документацию. Делегирование и новые расширения используйте только в пределах разрешённой задачи; не создавайте постоянные фоновые аудиты.
