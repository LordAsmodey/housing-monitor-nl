## Что понятно и что подтверждено

V2 отделяет технический сбор общего арендного каталога от персональных поисков и доставки. Google-вход, нормализованные города NL, фильтры на сервере, личная привязка Telegram с подтверждением из web и уведомления только о последующих NEW составляют первый пользовательский сценарий. Текущий каталог доступен в кабинете без рассылки baseline. Несколько поисков одного пользователя не создают повторную доставку одного NEW; доставка разным пользователям независима.

Обязательные условия: весь собственный исполняемый код переводится на TypeScript, источники проходят отдельную приёмку полноты, данные/IDs/история сохраняются, разработка и репетиции миграций идут на изолированном staging. Ошибки и partial runs не становятся успешным нулём; UNCERTAIN не отправляется повторно вслепую. Подробные watermarks, revision fences и connection generations уже описаны в разделах 7–9 плана; их нужно формализовать в A02–A05 до реализации matching/delivery.

Пользователь дополнительно подтвердил 31.10.2026:

- Первый интерфейс и сообщения — английские.
- Конфигурируемые лимиты: 5 поисков и 20 городов на пользователя, до 50 объявлений на странице. Правила подсчёта общей квоты городов и paused-поисков закрепляются в A03/I03.
- Отдельные тестовые Telegram-бот и Google OAuth-клиент созданы. Пользователь подтвердил добавление localhost callback, test user в Google (для режима Testing) и запуск бота через Start. Локально проверены наличие и формат переменных; реальная авторизация и Telegram linking ещё не проверялись.

Для первого локального этапа предусмотрен `http://localhost:3000/api/v1/auth/google/callback`; endpoint ещё не реализован. Секреты находятся в игнорируемом `.env.staging.local` (права при создании `0600`), в Git и PR не входят. Будущий запуск должен явно загрузить этот файл: существующие npm/Compose команды пока используют `.env`. Для Google нужны OAuth Client ID и Client secret, для Telegram — bot token и username без `@`; доставка и polling в файле выключены.

Обсуждён локальный стенд в Docker Compose с собственной БД/volumes и HTTPS-туннелем для проверки Telegram webhook. Он ещё не развёрнут. Long polling технически возможен, но не заменяет приёмку webhook из плана v2. Удалённое окружение и проверка deployment/HTTPS/cookies/реплик перед выпуском остаются отдельной работой; локальная подготовка не закрывает B03/B04/O06.

| Расхождение | Как поступать |
|---|---|
| Notion описывает админку v1 и общий поиск; multi-user отложен | Явно принятый план v2 меняет эту границу. Разделить пользовательский API и admin, сохранить отдельные полномочия |
| Backlog разрешает оставить небольшие CJS-оболочки | Требование v2 строже: собственные JS/CJS/MJS, тесты и программные конфиги должны исчезнуть полностью |
| В v1 изменение source filters создаёт тихий baseline поиска источника | В v2 пользовательские revisions не меняют сбор; нужны per-source activation watermarks и cancellation |
| Текущая доставка привязана к env-chat и source baseline | В v2 нужны personal connections, intents, поколения связи и независимый matcher |
| В v1 согласованы индивидуальные географические/ценовые условия источников | Национальный collection scope меняется явно по каждому адаптеру. Servicekosten/availability и source-specific валидацию не обобщать догадками |

Notion в этой подготовке не изменялся. A01 должен добавить согласованный контекст v2 на профильные страницы и явно заменить несовместимые пункты backlog до изменения поведения приложения. Открытые предложения из раздела 1 плана не считаются подтверждёнными автоматически.

## Что подготовить для staging

Это checklist будущих B03/B04, а не описание уже настроенного окружения. Удалённая конфигурация Railway в этой подготовке не инспектировалась.

| Ресурс | Требование до запуска |
|---|---|
| Railway | Отдельное изолированное окружение/проект, свой URL/DB/volumes; source branch `codex/platform-v2`; production credentials не копировать |
| Database | Отдельный DATABASE_URL, собственные учётные данные; мигратор проверяет целевое окружение до подключения/изменения схемы |
| Browser workers | Новые профили/ключи/volumes; live collection выключен до отдельной проверки лимитов |
| Telegram | Новый staging-бот через BotFather, токен в закрытом secret store; собственный webhook secret и URL. Не использовать production bot/chat/webhook |
| Google | Отдельный staging OAuth app/config, test users и точный callback на выделенном staging URL после A02/I01. Client secret хранится только на сервере |
| Runtime | До A06 явных ролей ещё нет: нельзя безопасно считать текущий API-процесс пассивным. Не запускать текущий app на общих данных ради проверки UI |
| Проверки изоляции | Неверное окружение блокирует запуск/миграцию/sender; staging test не может отправить сообщение production-пользователю; зафиксировать отрицательные проверки |

Тестовые bot/OAuth credentials уже подготовлены для локального этапа. До реализации B03/B04 нужно проверить их изоляцию от production, настроить загрузку секретов и точные callback/webhook параметры для выбранного URL. Для удалённого staging добавить его callback в Google и настроить собственный webhook; секреты не отправлять в чат или Git. Наличие credentials не означает работающий auth/linking или развёрнутый стенд.

## Правила следующей задачи

Указывать ID из основного backlog, integration base/ref, target PR `codex/platform-v2`, prerequisites, разрешённые пути, инварианты и команды проверки. Одна задача владеет изменением схемы/миграции; общий contracts barrel, bootstrap и lockfile имеют одного интегратора. Новые исполняемые исходники — TS. Production rollout не входит в подготовительные задачи; итоговый release идёт через R09 → R11 → R12.

До соответствующих этапов остаются решения о границах доступного каталога/unknown type, бюджете и задержке национального обхода, retention/privacy/RPO/RTO, отдельном public production bot и судьбе legacy-группы. Они не мешают инфраструктурной подготовке и не считаются согласованными по умолчанию.
