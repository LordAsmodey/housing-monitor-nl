# Housing Monitor NL

## Требования и контекст

- [docs/index.md](docs/index.md) — карта кода, runbooks и прямых ссылок на профильные страницы Notion.
- Источник требований — [Housing Monitor NL — требования и навигация](https://app.notion.com/p/3f6d10c6e6ab81fe8b06e6eebb9c9455). Явные указания пользователя имеют приоритет.
- Перед изменением поведения или планированием реализации сверяй актуальную **профильную** страницу Notion: конкретный источник, админку, архитектуру или backlog. Главную открывай, если нужная страница неизвестна. Для опечатки или оформления документации без изменения требований дополнительное чтение Notion не нужно.
- Читай только относящиеся к задаче файлы и разделы. Не перечитывай уже полученные неизменившиеся страницы в рамках одной задачи. Архивы, исследования и документы других источников открывай для конкретного вопроса.
- При недоступности Notion сообщи об этом и работай с локальным контекстом, не выдавая его за актуальную версию требований. Расхождения явно обозначай; не объединяй разные фильтры догадками.

## Выполнение

- Ищи сначала пути и совпадения через rg; затем читай нужные фрагменты. Не загружай весь репозиторий, docs или историю логов.
- Большие ответы инструментов фильтруй кодом до вывода в контекст. Для логов/тестов оставляй сводку и относящиеся к сбою детали; полный вывод при необходимости сохраняй во временный файл. Не скрывай ошибки и exit code, сохраняй возможность открыть оригинал.
- Объединяй независимые чтения в один вызов, возвращая только нужные результаты. Для новой гипотезы расширяй поиск адресно.
- Проверяй затронутое поведение и обязательные проверки проекта. Повторяй или расширяй проверки после изменений, ошибок или при конкретной неопределённости. Production-проверки выполняй, когда они нужны для поставленной задачи.
- Дополнительные правила диагностики, проверок и передачи контекста: [docs/agent-workflow.md](docs/agent-workflow.md); читай нужный раздел при соответствующей работе.
- Замеры токенов, фоновые аудиты, новые MCP/плагины и изменения модели не входят в обычную задачу без отдельного запроса.

## Режимы работы и субагенты

- Обычный запрос выполняй в текущем режиме: можно самостоятельно исследовать,
  менять файлы и проверять результат. Размер задачи сам по себе не включает
  полный процесс субагентов.
- Явные команды `implement: <задача>`, `/implement <задача>` или
  `$implement-feature` включают [.agents/skills/implement-feature/SKILL.md](.agents/skills/implement-feature/SKILL.md).
  `design: <задача>`, `/design <задача>` или `$design-feature` включают
  [.agents/skills/design-feature/SKILL.md](.agents/skills/design-feature/SKILL.md).
  Явная просьба пользователя работать оркестратором также включает указанный
  процесс. Упоминание команды в цитате, вопросе или примере не запускает его.
  Отдельные команды `implement`/`/implement` и `design`/`/design` без описания
  используют однозначную задачу из диалога; если её нет, сначала уточни цель.
- В этих процессах основной агент принимает роль
  [.codex/agents/orchestrator.toml](.codex/agents/orchestrator.toml): только
  координирует, проверяет результаты и передаёт минимально нужный контекст.
  Сам не пишет и не исправляет код, тесты, документацию, конфиги, миграции,
  прототипы или план реализации — включая мелкие исправления после ревью.
  План составляет Planner, содержательную работу выполняют профильные агенты.
- Все 14 ролей сохраняются. Реестр, команды, ограничения инструментов и
  примеры: [docs/subagents.md](docs/subagents.md). Общий контекст, технологии,
  константы и инварианты: [.codex/agent-context.md](.codex/agent-context.md).
- Workers обязаны проверять библиотечные API и подходы через доступный MCP
  Context7 для фактических версий зависимостей. Порядок resolve → query,
  переиспользование выдержек и честный fallback описаны в общем контексте.
- Для задач апдейта v2 ветки создавай от актуальной `origin/codex/platform-v2`,
  все промежуточные PR направляй в `codex/platform-v2`. `main` и production
  остаются для итогового release; см. [подготовку v2](docs/plans/platform-v2-preparation.md).
